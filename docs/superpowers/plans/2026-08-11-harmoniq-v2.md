# HarmonIQ v2 Implementation Plan — per-plan scoring, orientation gating, persistence, search

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax. Every task ends with a scoped commit.
>
> **Authoritative design:** [`docs/superpowers/specs/2026-08-11-harmoniq-v2-design.md`](../specs/2026-08-11-harmoniq-v2-design.md). Read it before your task. This plan gives you **contracts and constraints, not transcriptions** — where the design already decided something (rule text, arithmetic, copy), implement the design, don't re-litigate it. Design **§12 (local implementation scoping)** governs what actually gets built here.

**Goal:** Turn HarmonIQ from a stateless single-score-per-listing demo into a persisted, per-floor-plan, per-tradition scoring system with an orientation seam, a floor-plan vision lens, a versioned grades feed, and two demo host surfaces (mock LDP with per-plan chips, mock SRP with synonym search + HarmonIQ filter) — all runnable offline on one machine in demo mode.

**Architecture:** The v1 three-lens merge (`0.7·rooms + 0.3·site ± numerology` → one blended score) is replaced by a **perception/judgment split**: one tradition-agnostic vision call per subject writes an immutable `observations` row; deterministic per-principle-set derivation writes `analyses` rows keyed `(subject, principle_set, rules_version)`. Subjects are floor plans on multi-plan properties and the property itself on single listings. EF Core + SQLite is the store; report bodies go to a filesystem object store behind `IObjectStore`. Orientation arrives through `IOrientationProvider` (fixture provider locally, SightMap client stubbed). The frontend becomes three custom elements: a per-plan grade chip, a section element carrying the single attribution line and the single report drawer, and the slimmed single-listing card.

**Tech stack:** .NET 10 / ASP.NET Core, EF Core 9 + `Microsoft.EntityFrameworkCore.Sqlite`, xUnit (deterministic engines — **the v1 suite is replaced**), React 18 + TypeScript strict + Vite (IIFE, shadow DOM), Claude Messages API with forced tool calls (live path config-gated; demo mode is the local path), sharp (fixture plan images).

## Global Constraints

Every task implicitly includes these. Violating one is a task failure even if the acceptance steps pass.

**Build & process**
- **Demo mode is the development and verification path.** No Claude key exists on this machine and the hackathon proxy sunsets **Aug 12, 2026**. Every task must be verifiable with no key set. The live path stays wired behind config (`CLAUDE_API_KEY` + `CLAUDE_BASE_URL`) and is never required to prove a task done.
- **Green tree invariant:** every task leaves `dotnet build HarmonIQ.sln` and `npm run build --prefix frontend` green. Removing a v1 member is allowed **only** in the task that owns all of its call sites, or in a later tier. When in doubt, add alongside and delete later.
- **Pathspec-scoped commits.** Other agents commit concurrently in this same working tree. Never `git add -A`, never `git commit -a`. Always `git add <your files>` then `git commit -m "…" -- <your files>`. If `.git/index.lock` exists, sleep 3s and retry, up to 5 times.
- **One shared working tree, no branches** for Tiers 1–5. Tier 6 (apartments-web) is a different repo and a different branch.

**Engineering**
- Deterministic engines stay deterministic: site rules, coverage/confidence math, numerology, grade banding. No model call may influence a score — the model produces *observations*, the rules produce *scores*. The Refine drawer's predictable re-grade depends on this.
- **Never render a null/unscored state as a bad one.** `status = insufficient_evidence` renders as an explanatory absence, never `F`, `0`, an empty gauge, or five zero element bars. `ElementBalance` is nullable end-to-end (Feng Shui-only) and its section is *omitted* when absent.
- **No layout shift on the host page, ever.** Chips occupy their final footprint from first paint. The cold state is an identical-footprint muted box — no spinner, and never twelve spinners. Known-unscored subjects render **nothing** from the start.
- Shadow DOM isolation both directions (`:host { all: initial }`), `defer` script, no host breakage on any failure path, no hotlinking of listing media, no credentials client-side.
- A failure is never a grade: retries exhausted → `status = failed` → projection row stays NULL.
- **Demo output is never persisted.** Projection/publish writes require `mode = 'live' AND status = 'ok'`. Demo is a read-path presentation. (Locally this means the demo surfaces read computed-on-the-fly or seeded rows; the backfill command has an explicit `--demo` flag that writes to `analyses` but never publishes.)

**Guardrails that affect code (design §10)**
- Cultural framing everywhere: verdicts attributed to a named tradition ("in Chinese numerology…", "in form-school terms…"), never as objective claims about safety, health, or value.
- **No negative superlatives in any rule text, finding text, summary, or UI copy.** No "worst", "terrible", "cursed", "avoid this unit". Rule text describes the configuration and the tradition's reading of it.
- **Grades are never emitted into `<title>`, `<meta>`, or server-rendered host HTML.** They are client-rendered inside the shadow root only, so they are not indexable.
- Vastu grades are stored/filterable **only** where orientation resolved. A renter-supplied orientation in the Refine drawer yields a **session-only** score: displayed, never persisted, never filterable.
- The confidence floor (0.5) is non-negotiable — no low grade may ride thin evidence.

**Cross-task DI convention (this is how tasks stay parallel)**
`Program.cs` is edited **exactly once in the whole plan**, by Task 10. Every other task that needs DI creates its own `backend/HarmonIQ.Api/Infrastructure/<Area>Module.cs` implementing `IServiceModule` (created by Task 1); `Program.cs` calls `builder.Services.AddHarmonIQModules(builder.Configuration)`, which scans the assembly. **No task other than Task 10 may open `Program.cs`.** Module files have a single named owner per tier, listed in each task.

### Task 3: Prompts — tradition-agnostic room tool + floor-plan lens tool

**Files (exclusive ownership):**
- Modify: `backend/HarmonIQ.Api/Services/Prompts.cs`
- Create: `backend/HarmonIQ.Api/Models/LensModels.cs`
- Create: `backend/HarmonIQ.Tests/PromptSchemaTests.cs`

**Interfaces produced:**
- `Prompts.PromptVersion` — `const string = "v2.0"`. Bumping this invalidates observations; nothing else may define a prompt version.
- `Prompts.RoomSystemPrompt(string? orientationHint)` — **tradition-agnostic**. One call records *all* findings tagged by tradition; tradition filtering moves to score time (design §2, halves the LLM bill). There is no longer a `systems` parameter.
- `Prompts.RoomTool` — forced tool `record_room_observation`. Findings carry `ruleId`, `principle`, `observation`, `tradition` (`"fengshui"|"vastu"|"both"`), `confidence` (0–1). `elementBalance` is **optional** in the schema (Feng Shui-only).
- `Prompts.FloorPlanTool` — forced tool `record_floorplan_observation`. Schema requirements, all load-bearing:
  - `findings` and `suggestions` have **`minItems: 0`** — a forced call must be able to decline.
  - top-level `notDeterminable` (bool) + `notDeterminableReason` (string, optional) — the explicit decline marker.
  - every finding has `confidence` (number 0–1) and a `ruleId` drawn from a **closed enum** of adjacency-only rule ids: `bath_adjacent_kitchen`, `bath_over_kitchen`, `bath_door_onto_kitchen_dining`, `bath_door_onto_dining`, `entry_to_rear_straight_line`, `toilet_shares_bed_head_wall`, `center_obstruction`, `kitchen_at_entry`, `bed_wall_options`.
  - `boundaryFullyDrawn` (bool) — `center_obstruction` may only be reported when true.
  - `coverage` (number 0–1) — the model's own statement of how much of the rule catalogue the drawing let it evaluate; feeds `LensResult.Coverage`.
- `Prompts.FloorPlanSystemPrompt()` — must state the **out-of-scope list** as prohibitions: no furniture/staging claims, no mirrors, beams, clutter, natural-light quality, five-element balance, no dimensional claims, no door swings, and **no chirality-dependent (left/right) claims** because plans are mirrored for opposite building stacks. Findings must be adjacency-only. The lens must **never infer north** from the drawing; directional Vastu placement is a separate layer applied only when orientation exists.

`Models/LensModels.cs`:
- `record LensFinding(string RuleId, string Principle, string Observation, string Tradition, double Confidence, string? Severity)`
- `record RoomObservation(string PhotoId, string RoomType, IReadOnlyList<LensFinding> Findings, IReadOnlyList<Suggestion> Suggestions, ElementBalance? ElementBalance, double Coverage)`
